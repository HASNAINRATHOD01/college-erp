SECTION 1: EXECUTIVE SUMMARY & SYSTEM ARCHITECTURE

1.1 High-Level Purpose

Campuzz ERP is an enterprise academic management and intelligence web platform designed for higher education institutions (e.g., LJ University). It bridges administrative operations, faculty grading, daily attendance logging, and student self-service into a unified, secure system.

Core Problem Solved: Eliminates fragmented manual record-keeping, isolated grading sheets, and delayed academic interventions. It integrates an automated Machine Learning Performance Risk Predictor that analyzes real-time attendance and assessment records to predict student failure risk early in the academic semester.

1.3 End-to-End Data Flow Architecture

When an Admin runs an AI Performance Risk Assessment for a student:

  1. Client Trigger: User clicks Run Analysis in AdminDashboard.jsx.
  2. HTTP Dispatch: Sends POST /api/predict/ with payload {"student_id": 14} carrying Bearer <JWT_TOKEN> header.
  3. Auth & RBAC: Django's IsAuthenticated middleware validates JWT signature and verifies user role.
  4. Feature Extraction: predictions/views.py queries ORM to fetch marks and daily attendance for student #14, computing a 5-dimensional feature vector: [avg_percentage, attendance_pct, fail_count, top_grade_count, total_exams].
  5. ML Inference: The pre-loaded Random Forest model (rf_model.pkl) executes .predict(X) and .predict_proba(X).
  6. Logging & Response: Result saved to PredictionLog table and returned as JSON response to frontend.

2.2 Database Schema & Relationships

The database uses standard Relational Mapping via Django ORM:

  • User ↔ Student / Faculty: One-To-One Relationship (OneToOneField(User, on_delete=CASCADE)).
  • Student ↔ Attendance: One-To-Many (ForeignKey on Attendance.student). Unique constraint on (student, subject, date).
  • Student ↔ Mark: One-To-Many (ForeignKey on Mark.student). Unique constraint on (student, subject, exam_type).
  • Faculty ↔ TeacherClassAssignment: One-To-Many mapping faculty to course & semester divisions (D1 to D7).

SECTION 4: MACHINE LEARNING & DATA SCIENCE MODEL EXPLANATION

4.1 Dataset & Feature Engineering Pipeline

The AI Model predicts student risk levels by engineering 5 numerical features from database tables:

Feature Name Data Source Formula / Logic
avg_percentage marks_mark table Mean of (marks_obtained / max_marks) * 100 across all recorded subjects.
attendance_pct attendance_attendance table (total_present_days / total_conducted_classes) * 100.
fail_count marks_mark table Count of subject exams where percentage < 40%.
top_grade_count marks_mark table Count of subjects where grade is 'O' or 'A+'.
total_exams marks_mark table Total count of exam attempts recorded.

4.2 Why Random Forest Classifier?

  • Non-Linear Relationships: Academic failure is non-linear (e.g., high marks but 30% attendance still places a student at critical risk). Random Forest handles non-linear decision boundaries effectively.
  • Overfitting Resistance: By ensemble averaging 100 decision trees (n_estimators=100) trained on random bootstrap samples with max_depth=6, it prevents individual tree overfitting.
  • Imbalanced Data Handling: Configured with class_weight='balanced' to automatically adjust weights inversely proportional to class frequencies.

SECTION 6: ULTIMATE VIVA QUESTION & ANSWER BANK

Q1: Why did you choose a decoupled architecture with Django REST Framework and React instead of traditional Django HTML Templates?
Answer: A decoupled architecture separates concerns cleanly. Django serves exclusively as a stateless headless REST API handling business logic, database ORM, and ML model inference. React handles client-side rendering (SPA), resulting in sub-millisecond tab switching, lower server bandwidth consumption, and the ability to reuse the same backend APIs for future mobile apps (iOS/Android).
Q2: How does your application prevent the N+1 query problem when listing students with their associated user data?
Answer: We use Django's select_related('user') in our queryset definitions (e.g., Student.objects.select_related('user').all()). This forces Django ORM to execute an SQL INNER JOIN between the students_student and users_user tables in a single database query, instead of firing 1 query for the list plus N queries for each user record.
Q3: How does your AI model avoid data leakage during feature extraction and model training?
Answer: Data leakage is prevented by strict temporal and conceptual separation. Features such as avg_percentage and attendance_pct are calculated strictly from past historic database entries up to the current date. During training in train_model.py, train_test_split with stratify=y is executed before any model fitting, ensuring test set samples never influence model weights or feature scaling.
Q4: Explain how JWT Authentication works in your system and how token expiration is configured.
Answer: Authentication uses djangorestframework_simplejwt. Upon login (POST /api/token/), the backend verifies credentials and returns a signed access and refresh JWT token. In settings.py, we configured ACCESS_TOKEN_LIFETIME = timedelta(days=7) to ensure multi-day session persistence. Every request sends Authorization: Bearer <token> in headers, which Django verifies statelessly without hitting the session database.
Q5: How do you handle race conditions or database locks when multiple faculty members mark attendance simultaneously?
Answer: Attendance logging in AttendanceViewSet.create() uses atomic update_or_create() queries with explicit unique constraints on (student, subject, date). Sequential request handling on the client prevents SQLite table lock errors, and unique composite indexes at the DB layer reject duplicate insertion attempts at the engine level.
Q6: What measures were taken to handle imbalanced target classes in your machine learning dataset?
Answer: In academic datasets, 'at_risk' or 'excellent' students are naturally rarer than 'average' students. We handled this by setting class_weight='balanced' inside RandomForestClassifier. This automatically computes weights inversely proportional to class frequencies as n_samples / (n_classes * np.bincount(y)), giving higher penalties to misclassifications of minority classes.
Q7: Explain the line-by-line role of Nodemailer in your application's notification architecture.
Answer: Nodemailer is embedded inside Vite's Node.js development server middleware in vite.config.js. When an Admin or Faculty dispatches a notice, frontend executes an HTTP POST to /api/send-email. Node.js intercepts this, instantiates a Nodemailer createTransport targeting Gmail SMTP (smtp.gmail.com), injects the Google App Password, and calls transporter.sendMail() to deliver the message asynchronously under the hood.
Q8: What is the computational complexity of running your Random Forest inference per student request?
Answer: The inference time complexity is O(M × D), where M is the number of decision trees (100) and D is the maximum tree depth (6). Since M=100 and D=6 are fixed constants, inference runs in O(1) constant time (approx. 2 to 5 milliseconds per request), making real-time prediction lightweight and scalable.
