SECTION 1: SYSTEM ARCHITECTURE & DATA FLOW

1.1 Enterprise System Purpose

Campuzz ERP is a modern full-stack academic governance platform built to centralize university administration, faculty class grading, daily attendance registers, and student self-service portals into a unified single-page application.

Problem Solved: Eliminates fragmented paper logs, uncoordinated marksheets, and late academic risk detection. It features an automated Random Forest Machine Learning Predictor that analyzes historic marks and daily attendance to compute real-time failure risk assessments for early intervention.

1.2 End-to-End Execution Flow Architecture

  1. Client Trigger: Admin or Faculty clicks Run Analysis on a student profile in React.
  2. HTTP POST Dispatch: React fires POST /api/predict/ with payload {"student_id": 14} and header Authorization: Bearer <JWT_TOKEN>.
  3. Stateless Auth Validation: Django REST Framework passes the request through CustomTokenObtainPairSerializer to verify the JWT signature and role claims.
  4. ORM Feature Vector Extraction: predictions/views.py queries SQLite via Django ORM to aggregate student historic marks and attendance records into a 5-element feature vector: [avg_percentage, attendance_pct, fail_count, top_grade_count, total_exams].
  5. Inference Execution: The pre-loaded Random Forest model binary (rf_model.pkl) executes .predict(X) and .predict_proba(X) in constant $O(1)$ time.
  6. Audit Logging & Response: Result is stored in PredictionLog table and serialized as JSON back to the client UI.

2.1 JWT Authentication & Role-Based Token Customization

backend/users/serializers.py (Lines 8-30)
class CustomTokenObtainPairSerializer(TokenObtainPairSerializer):
    @classmethod
    def get_token(cls, user):
        token = super().get_token(user)
        # Embed custom RBAC claims into the JWT payload
        token['role'] = user.role
        token['username'] = user.username
        return token

    def validate(self, attrs):
        username_or_email = attrs.get(self.username_field)
        if username_or_email:
            username_or_email = username_or_email.strip()
            user = User.objects.filter(username__iexact=username_or_email).first()
            if not user:
                user = User.objects.filter(email__iexact=username_or_email).first()
            if user:
                attrs[self.username_field] = user.username

        data = super().validate(attrs)
        data['role'] = self.user.role
        data['username'] = self.user.username
        return data

Line-by-Line Breakdown: Overrides DRF SimpleJWT's default token generation. Lines 12-13 inject role (ADMIN, FACULTY, STUDENT) and username directly into the signed JWT payload. Lines 16-25 allow flexible login using either exact username or email address seamlessly.

4.1 Random Forest Model Training Script

backend/predictions/train_model.py (Lines 162-198)
from sklearn.ensemble import RandomForestClassifier
import joblib

# Instantiate Random Forest Classifier with anti-overfitting constraints
model = RandomForestClassifier(
    n_estimators=100,         # Ensemble of 100 decision trees
    max_depth=6,              # Limit tree depth to prevent memorization
    random_state=42,          # Fixed seed for reproducibility
    class_weight='balanced'   # Inverse frequency weighting for imbalanced classes
)
model.fit(X_train, y_train)

# Serialize trained model binary and exact feature schema
joblib.dump(model, 'predictions/ml_model/rf_model.pkl')
joblib.dump(FEATURE_COLS, 'predictions/ml_model/features.pkl')

Data Science Justification: Random Forest Classifier is chosen because academic performance risk boundaries are highly non-linear (e.g. 90% marks combined with 35% attendance places a student in 'critical risk'). Ensemble averaging 100 decision trees eliminates individual tree variance and prevents overfitting.

SECTION 6: ULTIMATE VIVA QUESTION & ANSWER BANK (30 EXAMINER QUESTIONS)

Q1: Why did you choose a decoupled architecture with Django REST Framework and React instead of monolithic Django Templates?
A decoupled architecture isolates backend business logic and database ORM from frontend presentation. Django functions strictly as a stateless JSON API engine. React provides sub-millisecond tab navigation, zero page reloads, and allows backend endpoints to be reused for future mobile applications.
Ref: frontend/src/apiService.js & backend/erp_backend/urls.py
Q2: How does your database query design prevent the N+1 select problem when listing students?
We utilize Django ORM's select_related('user') on queries (e.g., Student.objects.select_related('user').all()). This generates an SQL INNER JOIN between student and user tables in 1 query, avoiding N additional queries for user details.
Ref: backend/students/views.py:L138
Q3: How is JWT token lifetime configured, and why is access token lifetime set to 7 days?
In settings.py under SIMPLE_JWT, ACCESS_TOKEN_LIFETIME is set to timedelta(days=7). This ensures active administrative and student login sessions remain valid without forcing re-authentication every 2 hours.
Ref: backend/erp_backend/settings.py:L138
Q4: How does your AI model prevent data leakage between training and testing splits?
Data leakage is prevented by executing train_test_split(X, y, test_size=0.2, stratify=y, random_state=42) before fitting the Random Forest classifier. Test set feature vectors are strictly held out and never evaluated during parameter tuning.
Ref: backend/predictions/train_model.py:L168-L170
Q5: Explain how attendance is saved atomically when faculty members submit attendance registers.
AttendanceViewSet.create() calls Attendance.objects.update_or_create() indexed on (student, subject, date). This performs an atomic upsert in SQLite, preventing duplicate constraint violations and handling concurrent updates safely.
Ref: backend/attendance/views.py:L185
Q6: What is the computational time complexity of real-time prediction in your system?
Prediction time complexity is $O(M imes D)$, where $M=100$ (number of trees) and $D=6$ (max depth). Since both are fixed hyperparameter constants, real-time prediction executes in $O(1)$ constant time (approx. 3 milliseconds per request).
Ref: backend/predictions/views.py:L207
Q7: How did you handle class imbalance in student academic risk labels ('at_risk' vs 'good')?
We passed class_weight='balanced' to RandomForestClassifier. This automatically computes weights inversely proportional to class frequencies, giving higher penalties for misclassifying minority risk classes.
Ref: backend/predictions/train_model.py:L176
Q8: How does Nodemailer deliver email notices to Gmail without opening external popups or mail clients?
Nodemailer runs inside Vite's server middleware in vite.config.js. The frontend dispatches a background fetch('/api/send-email') HTTP request. Node.js processes the SMTP handshake via smtp.gmail.com:465 using Google App Passwords silently in the background.
Ref: frontend/vite.config.js:L58-L82
Q9: How are internal assessment exam marks (T1 to T4) synchronized across Faculty and Student dashboards?
When Faculty saves exam marks in FacultyDashboard.jsx, marks are saved under both student primary key ID and Roll Number in localStorage, and a custom event cms_marks_updated is dispatched. StudentDashboard.jsx listens to this event and re-renders live scores instantly.
Ref: frontend/src/FacultyDashboard.jsx:L398 & StudentDashboard.jsx:L226
Q10: What security measures prevent students from making AI predictions for other students?
predict_student_performance checks request.user.is_student. If true, it verifies that user.student_profile.id == student_id. If a student attempts to pass another student's ID, Django returns HTTP 403 Forbidden.
Ref: backend/predictions/views.py:L129-L134
